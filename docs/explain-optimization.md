# Анализ и оптимизация сложного SQL-запроса

## 1. Цель

Цель работы:

- взять сложную выборку с несколькими `JOIN`;
- использовать подзапрос;
- построить и проанализировать `EXPLAIN`;
- определить наиболее тяжёлые части плана;
- оптимизировать запрос;
- проверить, что результат после оптимизации не изменился;
- сравнить фактичское время выполнения.

Для анализа использовалась база данных `catalog_test`. В запросе участвуют таблицы:

```text
orders
order_items
products
categories
manufacturers
```

---

## 2. Версия MySQL и форматы EXPLAIN

Используется `MySQL 8.0.15`. В данной версии доступны основные представления `EXPLAIN` и `EXPLAIN FORMAT=JSON`. Также использовались:

```sql
EXPLAIN ...;
SHOW WARNINGS;
```

для просмотра преобразованного оптимизатором SQL и дополнительной информации.

Была выполнена проверка:

```sql
EXPLAIN FORMAT=TREE
SELECT 1;
```

MySQL 8.0.15 вернул:

```text
ERROR 1791: Unknown EXPLAIN format name: 'TREE'
```

Таким образом, третий современный формат `TREE` недоступен в используемой версии сервера. Для задания были зафиксированы три представления информации оптимизатора:

1. `EXPLAIN` в традиционном табличном виде;
2. `EXPLAIN FORMAT=JSON`;
3. `EXPLAIN` совместно с `SHOW WARNINGS`.

---

## 3. Исходный запрос

Запрос формирует отчёт о продажах товаров за последние 7 дней. Для каждого товара выводятся:

- товар;
- категория;
- производитель;
- количество заказов;
- количество проданных единиц;
- сумма продаж.

В результат поадают только товары, выручка которых выше средней выручки товара внутри соответствующей категории. Исходная реализация использовала коррелированный подзапрос в `HAVING`. Упрощённая структура:

```text
orders
    |
order_items
    |
products
    |
categories
    |
manufacturers
    |
GROUP BY product
    |
HAVING sales_amount >
    коррелированный подзапрос
        |
        orders
        |
        order_items
        |
        products
        |
        GROUP BY product
        |
        AVG(sales_amount)
```

## 4. Анализ исходного EXPLAIN

В исходном плане для таблицы `orders` использовался индекс:

```text
idx_orders_created_at
```

Основные показатели:

```text
type		= range
rows		= около 1940
filtered	= 33.33%
```

Также присутствовали:

```text
Using index condition
Using where
Using temporary
Using filesort
```

Это означает, что индекс ограничивап данные по `created_at`, но условие `status = 'Оплачен'` проверялось дополнительно. Наиболее тяжёлой частью плана стали:

```text
DEPENDED SUBQUERY
DEPENDED DERIVED
```

Во вложенной части повторно обрабатывались:

```text
orders
order_items
products
```

Причём `orders` снова читалась по диапазону примерно в 1940 строк. В плане подзапроса также присутствовал `Using temporary`. Исходный `EXPLAIN` явно показывает повторный проход через эти таблицы.

`SHOW WARNINGS` дополнительно подтвердил корреляцию подзапроса:

```text
Field or reference 'catalog_test.c.category_id'
of SELECT #3 was resolved in SELECT #1
```

То есть внутренний запрос зависел от `category_id` внешней выборки.

---

## 5. Основные тяжёлые места

### 5.1. Коррелированный подзапрос

Главная проблема:

```text
DEPENDED SUBQUERY
DEPENDED DERIVED
```

Для расчёта средней выручки категории выполнялась повторная агрегация продаж. Фактически одни и те же таблицы обрабатывались повторно:

```text
orders
order_items
products
```

Это оказалось наиболее дорогой частью запроса.

### 5.2. Индекс только по created_at

Условие запроса:

```sql
WHERE status = 'Оплачен'
  AND created_at >= ...
```

При этом существовал индекс только:

```sql
(created_at)
```

Поэтому MySQL сеачала находил заказы за период, а затем дополнительно фильтровал их по `status`.

### 5.3. Temporary и filesort

План также содержит:

```text
Using temporary
Using filesort
```

Они связаны с:

```sql
GROUP BY
```

оконной функцией после оптимизации и:

```sql
ORDER BY sales_amount DESC
```

`sales_amount` является вычисляемым значением:

```sql
SUM(quantity * unit_price)
```

поэтому обычный B-tree индекс не может заранее содержать результат в требуемом порядке.

## 6. Оптимизация запроса

Коррелированный подзапрос был удалён. Продажи сначала агрегируются один раз в CTE:

```text
weekly_product_sales
```

После этого средняя выручка товара внутри категории вычисляется оконной функцией:

```sql
AVG(sales_amount) OVER (
    PARTITION BY category_id
)
```

Структура стала следующей:

```text
orders
    |
order_items
    |
products
    |
categories
    |
manufacturers
    |
GROUP BY product
    |
weekly_product_sales
    |
AVG(sales_amount)
OVER (PARTITION BY category_id)
    |
filter
sales_amount > category_avg_sales
```

После переписывания из плана полностью исчезли:

```text
DEPENDED SUBQUERY
DEPENDED DERIVED
```

Базовые таблицы стали обрабатываться одни основным проходом.

---

## 7. Оптимизация индекса

Для условия:

```sql
status = 'Оплачен'
AND created_at >= ...
```

создан составной индекс:

```sql
CREATE INDEX idx_orders_status_created_at
    ON orders (status, created_at);
```

Порядок полей выбран как:

```text
status
created_at
```

Поскольку сначала используется условие равенства:

```text
status = ...
```

а затем диапазон:

```text
created_at >= ...
```

После создания индекса была обновлена статистика:

```sql
ANALYZE TABLE orders;
```

До индекса:

```text
key		= idx_orders_created_at
rows		= около 1938
filtered	= 33.33%
```

После:

```text
key		= idx_orders_status_created_at
rows		= около 1162
filtered	= 100.00%
```

Также появилось:

```text
Using index
```

Таким образом, фильтрация по статусу и периоду стала выполняться непосредственно через составной индекс.

## 8. Проверка эквивалентности

Для обоих вариантов использовалась одна фиксированная граница периода. Исходный запрос вернул:

```text
1720 строк
```

Оптимизированный запрос:

```text
1720 строк
```

Затем результаты были сравнены в обе стороны. Строки, существующие только в исходном результате:

```text
Empty set
```

Строки, существующие только в оптимизированном результате:

```text
Empty set
```

Таким образом, оптимизация не изменила результат запроса.

## 9. Сравнение времени выполнения

Для изменения результаты запросов записывались во временные таблицы, чтобы вывод 1720 строк в терминал не влиял на время.

### Исходный запрос

Получено:

```text
1720 строк
28675.800 ms
```

Фактическое выполнение создания результата заняло около 29 секунд.

### Переписанный запрос без нового индекса

Получено:

```text
1720 строк
141.777 ms
```

### Переписанный запрос с составным индексом:

После создания:

```sql
CREATE INDEX idx_orders_status_created_at
    ON orders (status, created_at);

ANALYZE TABLE orders;
```

получено:

```text
1720 строк
109.935 ms
```

Сводная таблица:

| Вариант | Время |
|---|---|
| Исходный запрос | 28675.800 ms |
| Переписанный запрос | 141.777 ms |
| Переписанный запрос + индекс | 109.935 ms |

Основной прирост производительности получен за счёт устранения коррелированного подзапроса. Переписывание запрос уменьшило время примерно в 202 раза. Добавление составного индекса дало дополнительное ускорение примерно в 1.29 раза относительно уже переписанного запроса. Итоговое время уменьшилось примерно в 261 раз относительно исходной реализации.

## 10. Вывод

Наиболее тяжёлым местом исходного запроса оказался не `filesort` и не отсутствие отдельного индекса, а алгоритм выполнения коррелированного подзапроса. Исходный вариант содержал:

```text
DEPENDED SUBQUERY
DEPENDED DERIVED
```

и повторно агрегировал продажи для категорий. Основная оптимизация заключалась в изменении алгоритма:

```text
коррелированный подзапрос
        ->
однократная агрегация
        ->
оконная функция
```

Дополнительно был создан индекс:

```text
orders(status, created_at)
```

который улучшил фильтрацию заказов по статусу и временному диапазону. После оптимизации:

- результат запроса остался неизменным;
- зависимые подзапросы исчезли;
- число кандидатов при чтении `orders` уменьшилось;
- фильтрация стала выполняться через составной индекс;
- фактическое время уменьшилось с примерно 28.7 секунды до примерно 0.11 секунды.

При этом `Using temporary` и `Using filesort` полностью не исчезли, поскольку они обусловлены характером самой аналитической задачи: группировкой, оконной функцией и сортировкой по вычисляемой агрегировнной величине.
